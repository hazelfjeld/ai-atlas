Benchmark

A standardized task, dataset, or protocol for comparing systems.

Expanded guide · editorial review 2026-11-02. Original definitions, examples, notes and citations are preserved below. New examples are illustrative, not benchmark results.

Mechanism: what a benchmark standardizes

A benchmark defines the task population, permitted inputs and actions, scoring procedure, and conditions for comparing systems. The dataset alone is not the protocol: prompts, tool access, budgets, environment resets and grader versions can all change outcomes. A leaderboard is a particular collection of scores, not independent evidence of broad capability.

Defining success and the denominator

For N eligible tasks, observed completion rate is independently verified successes divided by N. Specify whether timeouts, invalid actions, crashes and refusals count as failures before evaluating. When an agent can modify an environment, check final task state and forbidden side effects; do not accept the model's assertion of success as a substitute.

Worked synthetic paired comparison

Suppose two models attempt the same 20 held-out tasks with equal tool budgets. Model A completes 13/20=65% and B completes 15/20=75%, a ten-percentage-point observed difference. This is a toy arithmetic example, not an actual measured model benchmark; twenty cases cannot show reliable superiority without paired outcomes, uncertainty estimates and multiple trials.

What interactive evaluations measure

AgentBench assesses agents over eight multi-turn interactive environments. OSWorld initializes desktop states and uses execution-based evaluators; SWE-bench judges repository patches using tests. These source-published benchmarks differ in tasks, tool scaffolds and graders. A score on one does not automatically transfer to new operating environments or certify safety.

Build a reproducible test harness

Freeze task IDs, initial state snapshots, software versions, instruction templates, tool schemas, evaluator code, random seeds, limits on time and actions, and success criteria. Record action trajectories, tool errors, observed side effects, environment state and resource use. Keep checksums for test manifests and disclose any reruns with a changed grader.

Prevent contamination and metric gaming

Maintain separate development, calibration and sealed test sets. Audit near-duplicate tasks and possible training overlap; repeated optimization against public or leaked benchmark items encourages overfitting. Include distribution-shifted cases and intentional grader probes. Improved pass rates are insufficient evidence of underlying skill if evaluation artifacts can be exploited.

Distinguish failures from grading errors

String-matching a final message can falsely pass a failed tool operation; overly rigid output matching can reject equivalent valid answers. Manually audit a blinded sample of apparent passes and failures, including unauthorized effects. Record evaluator disagreement, tool exceptions and task ambiguity instead of collapsing all outcomes into one number.

Design a fair ablation and report its limits

Compare identical tasks, tools, attempts and compute budgets; vary one system component at a time. Report per-domain completion, uncertainty, safety violations and cost rather than only the pooled mean. Control for sampling and nondeterministic environments. Benchmark results remain conditional on these experimental assumptions and cannot prove general alignment.

Terminology and real-world evidence boundaries

The phrase 'environment-grounded agent benchmark' is descriptive of an interactive evaluation design, not established by these papers as an independent technical standard. Environment-based benchmarking is useful, but an engineered success or exploit in a controlled test is not automatically a deployed incident. Explicitly label illustrative data, author-reported results and independently replicated findings.
