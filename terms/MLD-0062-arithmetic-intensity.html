Systems and efficient execution · MLD-0062

Arithmetic intensity

The ratio of arithmetic work to data transferred, commonly operations per byte.

Expanded guide · editorial review 2026-11-03. Original definitions, examples, notes and citations are preserved below. New examples are illustrative, not benchmark results.

Prerequisites

  • Memory bandwidth
  • Floating-point operation count
  • Throughput

Arithmetic intensity from first principles

Arithmetic intensity is useful work divided by bytes moved across a specified memory boundary, usually FLOP/byte for a chosen kernel. A device cannot perform a multiplication with an operand it has not received. Increasing the reuse of data can raise the number of operations done per byte fetched, but only after defining which operations and which memory layer the ratio counts.

The roofline relationship

If achievable compute throughput has ceiling Ppeak and the memory layer delivers at most B bytes/s, performance obeys P <= min(Ppeak, B times I), where I is FLOP/byte. This is a bound, not a predicted benchmark score. The transition between memory-limited and compute-limited regions occurs at intensity Ppeak/B; real kernels can fall below both roofs for scheduling, synchronization or instruction inefficiency.

Worked synthetic kernel classification

Suppose a kernel executes 12 million floating-point operations and moves 8 million bytes to and from device DRAM. Intensity is 12/8 = 1.5 FLOP/byte. At an illustrative sustainable 600 GB/s, the memory roof is 0.9 TFLOP/s. A 12 TFLOP/s compute roof would not be reachable through that traffic pattern; no actual GPU or benchmark is being reported.

Calculate the ridge point with units

Under the same assumed 12 TFLOP/s compute peak and 600 GB/s bandwidth, the ridge point is 12,000 GFLOP/s divided by 600 GB/s = 20 FLOP/byte. Below 20 FLOP/byte the model's memory roof is lower; above it the compute roof is lower. The threshold changes with hardware, arithmetic precision and which cache or memory level supplied B.

Data reuse and a controlled counterexample

Imagine 128 million FLOP requiring 64 MB of DRAM traffic: intensity is 2 FLOP/byte. A valid tiling change that halves off-chip traffic to 32 MB raises it to 4 FLOP/byte, but could slow execution if it adds synchronization or register spills. Run an identical-output A/B comparison, observe actual DRAM counters and latency, and do not infer faster execution from intensity alone.

Matrix multiplication versus matrix-vector multiplication

Multiplying large dense matrices can reuse blocks of operands many times, while repeated matrix-vector steps at small batch sizes often reuse each weight less. Thus increasing batch size can change measured arithmetic intensity and the active bottleneck. This is a conditional explanation for why prefilling an LLM prompt and decoding one token can stress very different parts of the same accelerator.

How to profile the right level

Collect FLOP counts and bytes for the same operation and memory hierarchy with a profiler rather than combining host-transfer bytes with device-kernel FLOPs. NVIDIA Nsight Compute supports hierarchical rooflines for device memory and caches. Cross-check the relevant arithmetic type, cache counters and optimized instruction path; a tensor-core estimate must not silently use a scalar FP32 roof.

Where edge near-memory designs fit

A near-memory chip can reduce expensive transfers without increasing the raw FLOP count. Tohoku University and AISIN's November 2 STT-MRAM demonstration is a controlled illustration of minimizing external weight and boot-data movement. Its publisher-reported power-on and energy figures are architecture- and model-dependent; they do not supply a general roofline measurement for other devices.

Interpretation, limitations and reproducibility

A high computed FLOP/byte ratio is not an accuracy or reliability metric, and low intensity is not evidence of poor engineering when the workload is inherently streaming. Include operation-count conventions, bandwidth layer, batch dimensions, cache behavior, precision and repeated timings in any comparison. Roofline analysis prioritizes bottlenecks, but only a measured and reproducible optimization establishes a real improvement.
