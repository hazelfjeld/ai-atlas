Security, privacy, and fairness · MLD-0957

Prompt injection

Instructions embedded in lower-trust input that attempt to override intended system behavior or authority boundaries.

Expanded guide · editorial review 2026-11-02. Original definitions, examples, notes and citations are preserved below. New examples are illustrative, not benchmark results.

Prerequisites

  • Agentic workflow
  • Indirect prompt injection
  • Red teaming
  • Retrieval-augmented generation

The trust boundary at the center of the attack

Prompt injection occurs when an instruction-like string from a lower-trust surface is treated as if it had authority over the assistant's intended job. The underlying issue is not unusual wording: it is promotion of untrusted content into the control plane. Legitimate user requests, developer policy and retrieved evidence have different permissions, even if all three arrive as text.

Direct injection versus indirect delivery

A direct attempt may appear in adversarial user input; an indirect attempt travels inside a page, email, file, repository comment or tool response that the assistant was asked to inspect. Both try to redirect behavior, but the indirect case is especially easy to miss because the malicious text is encountered during an otherwise authorized task. Not every quoted imperative is an attack.

Mechanism: data looks like instructions

Models interpret natural language across concatenated contexts, and delimiters by themselves are not security permissions. A retrieved snippet that claims to be a system message can be semantically salient even though its origin has no authority. The correct system design treats the snippet as task data, applies application-level authorization to subsequent tool calls and prevents model-generated text from granting its own privileges.

Worked synthetic support-assistant example

A user asks for the shipping status of an order. A retrieved product note includes a fabricated instruction to mark the order refunded. The safe path is to summarize the note as evidence, read shipping status through a read-only tool and refuse any refund mutation unless an independently authenticated user request and policy check authorize it. This scenario is invented for teaching, not a reported breach.

Threat modeling and measurable consequences

Describe the legitimate user goal, attacker-controlled surface, desired deviation, trust boundary, available tools and side effects. A model parroting a suspicious phrase differs from an agent making an unauthorized tool call; both differ from an actual ledger change. Record which occurred, not a single undifferentiated 'jailbreak success' label. Data leakage, answer contamination and unauthorized actions need separate outcome checks.

Defense in depth outside the prompt

Prefer narrowly scoped tool credentials, typed parameters, allowlisted destinations, execution-layer permission checks, non-executable document rendering, sandboxing, confirmation for sensitive writes and provenance-aware retrieval. A prompt saying 'ignore malicious instructions' is at best one layer. Input classifiers and sanitization may reduce exposure, but can miss novel payloads or incorrectly reject legitimate documents; measure both errors.

Evaluation protocol using bounded simulations

Construct benign tasks paired with untrusted snippets and explicit forbidden side effects. Evaluate a baseline without attacks, then with attacks under the same model, tools and budget. Log tool trajectories and final state; estimate user-task success, attack success, false positives and cost separately. Test adaptive variations on a held-out suite; leaking the test cases into a prompt or model tuning procedure invalidates simple generalization claims.

Pseudocode for an authorized tool boundary

For each proposed action: validate a structured schema; bind it to the authenticated user and granted scope; reject unknown resource IDs or destinations; request human approval when required; execute in a sandbox; log actual effects; return a bounded observation. Re-parse untrusted tool outputs as data on every loop. This is architectural pseudocode, not a formal proof or a substitute for implementing access control.

Limitations and common misconceptions

Prompt injection is not equivalent to ordinary factual errors, model jailbreaks or training-data poisoning, although these can overlap. A scanner reporting 'no injection detected' does not establish that an agent is safe, and a successful controlled red-team attack is not automatically evidence of deployment-wide compromise. OWASP and AgentDojo describe risk patterns and benchmark settings; mitigations should be independently tested against the application's exact tools.
