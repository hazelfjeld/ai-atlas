Agents and tool use · MLD-0043

Agentic workflow

A workflow giving a model some control over sequencing, branching, or tool selection.

Expanded guide · editorial review 2026-11-02. Original definitions, examples, notes and citations are preserved below. New examples are illustrative, not benchmark results.

Prerequisites

  • Tool use
  • Structured output
  • Agent evaluation
  • Environment

Mechanism: control flow belongs to the system

An agentic workflow joins a model's decisions to an explicit execution loop: inspect the task and state, choose an allowed action, validate the request, call a tool, observe its result, and either continue or stop. The surrounding application (sometimes called the agent harness) owns the tool schemas, retries, permissions, memory and termination policy. The model is one component, not the entire system.

Fixed workflow versus adaptive agent

A deterministic chain has predetermined stages such as classify → retrieve → draft → check; it may use an LLM at each stage without giving the model control of the next step. An adaptive agent chooses a branch, tool or subtask based on observations. Anthropic describes both patterns, noting the reliability, cost and latency tradeoffs of extra autonomy. Neither label implies that a system performs well.

Worked example: constrained support triage

Imagine a support assistant that first classifies a request, retrieves a relevant order with a read-only tool, and drafts an answer. A refund operation requires a separate human approval and a narrowly scoped write tool; a model's text saying 'refund issued' does not change the ledger. The harness records approval, tool inputs and final state. This is an illustrative design, not an observed production deployment.

Pseudocode: separate choice from execution

At each step: (1) obtain an observation from the sandbox; (2) request one structured action from the model; (3) parse the action against a schema; (4) authorize the target and arguments; (5) execute with a timeout and log the side effect; (6) update state; (7) stop on success, denied action, budget exhaustion or human escalation. Authorization must be implemented outside the model's own instructions.

Concrete applications and boundaries

Useful scenarios include document extraction followed by validated database writes, coding assistance with sandboxed tests, and browser research that cites the retrieved pages. Prefer a simple fixed workflow when the route is predictable; use dynamic tool selection when observations genuinely determine the next step. A long sequence of model calls is not automatically an autonomous agent.

Failure taxonomy: skill, objective and permissions

A missed field may be a capability failure or ambiguous input; a deliberate-looking sequence that optimizes a proxy metric can instead be specification gaming. Tool calls, final database state, observed side effects and the written instruction must be compared before classifying either. An unauthorized call in a constructed test does not by itself establish a persistent real-world goal or intent.

Evaluation beyond happy-path completions

Create held-out tasks with explicit success criteria, forbidden side effects and a fixed tool environment. Record final state, tool trajectory, argument validity, timeouts, token and cost budgets, and recovery from partial failures. Audit false passes from self-reported success and false fails from overly strict exact-match graders. Repeat across task families and changed tool responses; treat a benchmark score as scoped to its harness and tasks.

Security and observability requirements

Use least-privilege service credentials, typed tool schemas, independent authorization and policy checks, sandbox boundaries, rate limits, human approval for irreversible operations, and tamper-resistant audit logging. OpenAI's Agents SDK documents tool guardrails and handoffs, but those are framework-specific controls with different coverage: a handoff is not automatically checked by a function-tool guardrail. Confirm actual behavior in the installed version.

Misconceptions and experiment design

An agent harness is infrastructure for running and observing agents, not a universally standardized algorithm or a synonym for agentic workflow. Adding more tools or loops does not guarantee better reasoning, safety or task completion. Test a fixed workflow baseline against an adaptive variant under the same budget; changes in prompts, tool availability or evaluators can confound the comparison.
