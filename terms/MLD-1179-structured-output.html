Decoding and inference behavior · MLD-1179

Structured output

Model output organized to satisfy an explicit schema or format.

Expanded guide · editorial review 2026-11-03. Original definitions, examples, notes and citations are preserved below. New examples are illustrative, not benchmark results.

Prerequisites

  • Constrained decoding
  • Tool schema
  • Exact match

A schema is a contract, not an answer key

Structured output means that a model returns a value in an agreed representation, often JSON, with named fields and specified types. The consuming application can parse and validate that representation before using it. A JSON object may be syntactically valid while semantically false: a correctly typed event_time or count can still be invented, swapped, misread or omitted through an allowed null.

Three different levels of correctness

First test that the response parses as JSON or another required language. Second validate its structure against the exact schema, including required keys, enums, value types and additional-property rules. Third check the meanings of the extracted values against source evidence. A parser, a JSON Schema validator and an independent task-specific oracle answer different questions; none substitutes for the others.

How constrained decoding changes generation

A constrained decoder restricts the next token choices to those compatible with a supplied grammar or supported schema. For instance, it may prevent an extra property from appearing where additionalProperties is false. It cannot force the model to know a missing source value. Enforcement also varies by backend and supported schema subset; a request for unsupported keywords may be rejected or handled differently by model and server versions.

Worked example with valid but incorrect values

Imagine a source message stating that service A returned status 503 after 120 ms. The target object has required keys service:string, status:integer and latency_ms:integer, with no extra properties. Both {"service":"A","status":503,"latency_ms":120} and {"service":"A","status":200,"latency_ms":120} satisfy that shape; only the first matches the stated input. This constructed counterexample explains why even perfect schema adherence is not a guarantee of accurate extraction.

Missing data, null and duplicate-key policies

Specify whether a missing field must be null, absent, an explicit error or a sentinel value; do not let each model choose independently. Decide whether null is allowed by the schema and whether an empty string has a different meaning. Also define duplicate-key behavior, array ordering, timezones, units and numeric rounding before scoring, because two formally parseable outputs can encode different semantics.

A reliable extraction pipeline

Version the input grammar and output schema. Supply the source with provenance, run schema-constrained generation when supported, parse with a real JSON parser, validate with the declared schema, then verify field values against a held-out annotated oracle or deterministic parser. Quarantine mismatches and unknown fields; keep raw input, model version, schema version, decoding parameters and failure category for reproducibility.

How to measure performance without hiding errors

Report valid-JSON rate, schema-compliance rate, all-fields-correct exact match and field-level accuracy separately. Consider an error taxonomy for missing/null fields, transposed values, unit conversions and noisy source syntax. Use a fixed untouched test split and stratify by source grammar and failure class. A benchmark with only generated inputs may expose useful regressions but cannot establish real production generalization.

Threats from untrusted source text

When the source is a log, document or retrieved page, embedded instructions are data to extract from, not directions to override the schema or invent fields. Treat schema-conformant yet malicious values as untrusted until authorized downstream validation. Avoid logging private records without consent and test adversarial input, malformed encodings, very long fields and prompt injection separately from benign format compliance.

Case study and evidence boundary for IFParse v2.0

An author-described November 2026 IFParse v2.0 benchmark proposes nine synthetic telemetry grammars and strict extraction scoring. Its dataset card was not accessible through this Atlas editorial review, so sample integrity, row counts, evaluator semantics, licenses and reported model scores were not independently reproduced. Use the proposal as a motivation for checking parseability, schema compliance and field correctness, not evidence that any model succeeds in a real production pipeline.

Decision criteria and common misconceptions

Choose structured generation when downstream tools need typed, predictable arguments or machine-readable extraction; choose a deterministic parser when the input grammar is known and stable. Always check that the chosen inference backend supports the exact schema subset you rely on. JSON mode does not imply schema adherence; schema adherence does not imply semantic truth; a synthetic benchmark score does not imply field safety, security or general deployment readiness.
