Reinforcement learning · MLD-0371

Environment

The system an agent interacts with, receiving observations and producing consequences and rewards.

Expanded guide · editorial review 2026-11-02. Original definitions, examples, notes and citations are preserved below. New examples are illustrative, not benchmark results.

Prerequisites

  • Agent
  • State
  • Agentic workflow
  • Benchmark

Mechanism: the environment supplies consequences

An environment accepts actions, updates task-relevant state and returns observations, and sometimes a reward. It may be a game, software sandbox, tool API, browser or controlled simulator. The agent can see only a partial observation of state; its final text does not itself establish that an intended operation changed the world.

Transition dynamics from first principles

A Markov decision process represents transitions as s_next drawn from P(s_next | s, a), where a is the agent's selected action. The environment, not the agent's narrative, determines what follows. A policy may receive observation o rather than the complete state s, which matters for hidden permissions, stochastic events and partial observability.

Gymnasium reset and step semantics

Gymnasium's reset() initializes an episode, and step(action) returns observation, reward, terminated, truncated and info. Terminated indicates a task-defined terminal state, while truncated may be a time or step budget stop. Treating truncated as task success conflates running out of time with reaching the intended goal; treating it as termination can distort training.

Worked synthetic customer support setting

Imagine states {open, verified, resolved} with actions {lookup, draft, issue_refund}. The environment rejects refund execution unless approval exists, and the agent receives an observation reflecting this refusal. A final message saying 'refund completed' changes no ledger state. This is a synthetic teaching example, not an observed business deployment.

Where authorization belongs

Use typed tools and execution-layer least privilege to enforce permitted actions, track durable side effects, rate limit calls and separate read-only from destructive operations. A model's own policy prompt cannot replace independent permission enforcement. A sandbox also requires isolation testing; naming it a sandbox does not guarantee security.

Why interaction benchmarks expose different failures

AgentBench tests iterative decisions and feedback in multiple interactive settings. OSWorld configures real desktop applications and checks execution results. Such tasks can reveal navigation mistakes or unobserved state changes that a static question dataset misses. Their reported benchmark scores are author-scoped experimental results, not guaranteed performance in production.

Resetting between experimental trials

Record the environment image, dependency versions, tool configuration, evaluator hash, random seed and task setup. Reset state before each attempt and detect leftover files, cached credentials, changed web content or rate limits that contaminate later trials. If a true reset is not available, report nondeterminism and repeat samples rather than assuming independence.

Diagnose full trajectories and possible proxy gaming

Measure final state success, invalid operations, forbidden side effects, step counts, time and cost. Inspect action traces to distinguish capability failure, ambiguous instructions, evaluator false positives and possible specification gaming. Reaching a reward trigger without the intended state warrants analysis; it does not by itself demonstrate deception or an actual safety incident.

Limits and misconceptions

An environment is not synonymous with a reward function, a physics simulator or the unrestricted internet. A simplified world improves repeatability but may omit safety-critical hidden variables and deployed API behaviors. Controlled tests support useful ablations only when those assumptions and permissions are explicit.
