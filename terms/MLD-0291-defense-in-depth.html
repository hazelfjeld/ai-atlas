AI safety and alignment · MLD-0291

Defense in depth

Using several independent or complementary protective controls rather than one barrier.

Expanded guide · editorial review 2026-11-03. Original definitions, examples, notes and citations are preserved below. New examples are illustrative, not benchmark results.

Prerequisites

  • Prompt injection
  • Indirect prompt injection
  • Data provenance
  • Red teaming

What layered protection means

Defense in depth places distinct security controls at different boundaries so a single failure need not cause the protected action. In an LLM agent, relevant layers may include data provenance, a model instruction hierarchy, tool-call authorization, sandboxing, independent verification and a human decision for high-impact changes. The term is a security-engineering strategy, not a model architecture or a claim that adding more prompts makes a system secure.

Follow the trust boundaries

Map every path by which untrusted text can influence a decision: retrieved web pages, repository files, tool responses, user messages, stored memories and model-generated arguments. Treat these as data unless separately authorized. The model may suggest an action, but the application should check identity, resource ownership, arguments and permissions before a tool runs. A document's apparent authority cannot grant application permissions.

A concrete agent workflow

Suppose a research assistant reads a third-party PDF and drafts a summary. The document contains a forged instruction to email an internal customer list. A source-labeling layer identifies it as external content, the instruction policy tells the model not to obey it, an independent outbound-mail gate lacks permission to read the list, and a human approval gate covers any legitimate external send. Each is a different check; quoting the malicious text as evidence is not permission to act on it.

Toy arithmetic for conditional layers

For a deliberately synthetic 100-attempt evaluation, imagine an initial provenance gate stops 30 attempts; among the remaining 70, authorization rejects 60; among the remaining 10, confirmation rejects 9. One reaches the protected action, a constructed 1/100 end-to-end rate. More generally P(reach action)=P(pass A)*P(pass B | pass A)*P(pass C | pass A and B). Multiplying three unconditioned pass rates would silently assume independence and can give a wrong estimate when failures are correlated.

Prioritize the decisive non-model gates

The strongest boundary is often a capability the model never receives: read-only database credentials, per-user API scope, allowlisted destinations, a sandbox with no production keys, or an operation that requires a separately authenticated human. Output filters and refusals can reduce attempted misuse but must not substitute for server-side authorization. Do not expose secrets and then rely on a prompt asking the model not to leak them.

Build a realistic evaluation harness

Create a sandbox with a legitimate objective, documents of varying trust, adversarial instructions, tool permissions and a defined forbidden final state. Log proposed calls and accepted calls separately; independently inspect the final environment, not only the model's explanations. Include hidden tests for paraphrased and multilingual attacks, encoding changes, failed tool responses and attempts to launder instructions through citations.

Measure security and usefulness separately

Track attack success rate against the protected state, unauthorized tool-call rate, number of blocked actions, benign-task completion and false-positive rate. Report denominators and confidence intervals, because a small red-team suite can make a weak system appear flawless. Include latency, cost, usability and approval burden. Compare layers individually and together in an ablation study so correlated safeguards are not mistakenly credited as independent protection.

Contain failures and plan recovery

On a suspected injection, preserve minimal privacy-safe provenance, halt high-risk tool permissions, rotate exposed test credentials where warranted and route the event for human review. Make writes reversible with transaction boundaries, audit logs and rollback. Even a robust model can encounter a compromised tool or badly configured policy; incident handling, access reviews and secure operations remain necessary.

Limits and common misconceptions

Defense in depth does not mean stacking several copies of the same prompt filter: correlated failures can bypass them all. A successful controlled sandbox test does not prove safety in a different deployment, model release or permission configuration. A blocked prompt is not proof of attacker intent, while an allowed response is not automatically evidence of a completed breach. Reassess controls when tools, data flows or credentials change.
